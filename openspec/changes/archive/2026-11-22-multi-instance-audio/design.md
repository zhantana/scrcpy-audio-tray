# 设计

## 为什么不是「让两路都有声音」

做不到。Android 的 remote submix 只有一个输入端口，后注册者会覆盖前面的。scrcpy 官方也确认抓音频用的是 `AudioRecord` + remote submix，不是播放捕获 API。

同一台手机同一时刻只有一路能出声音，这是平台边界。

## 怎么发现「声音被带走」

进程活着不代表有声音，Windows 端也看不出「音频有流但没数据」。所以不检测音频数据本身，而检测**事件**：别的 scrcpy 实例数量变少了。

- 基线在每次 `Start-Audio` 完成后记录（此时自己的进程已起来，不会把自己算进去）
- 每秒比对一次，数量减少即判定「有人关了投屏」
- 延迟两拍（约两秒）再重启，给 Android 释放音频通路留时间

数量变多时不处理：后开的实例会抢走声音，但主动抢回会造成两个程序互相踢。

## 为什么最后是整路重启

原计划是拆成两个进程，只重启声音那一路，让画面不闪。实测否决：

| 场景 | 8 秒内 `Buffering threshold exceeded` 次数 |
|---|---|
| 单进程（画面 + 声音） | 0 |
| 视频 `--no-audio` + 独立音频进程 | 17 |

拆开后音频持续丢样本，表现为没声音或声音碎裂。原因指向两个 scrcpy 客户端同时存在时的音频时钟/缓冲异常，短期内无法在参数层面解决。

因此回到单进程，接受「整路重启、画面闪断一两秒」这个代价。

## 实测

| 项目 | 结果 |
|---|---|
| 单进程投屏（`--turn-screen-off` + 音频） | 8 秒 0 次丢样本，音频解码正常 |
| 拆进程 | 8 秒 17 次丢样本，否决 |
| 脚本语法 / 编码 | 通过，UTF-8 BOM，无纯 LF |
